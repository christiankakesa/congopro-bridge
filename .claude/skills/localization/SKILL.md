# Localization Skill — The i18n/l10n Bible

## 0. Mission

Treat localization as a product architecture concern, not as a translation step.

This skill governs:

- internationalization (i18n): designing software so language and regional variation
  can be changed without changing product logic;
- localization (l10n): adapting the product to a language, locale, region, culture,
  and market;
- translation: rendering source content naturally and accurately in the target language;
- regionalization: adapting dates, numbers, currencies, units, addresses, names,
  phone numbers, legal content, defaults, calendars, time zones, and other regional
  conventions;
- terminology management and linguistic consistency;
- locale-aware formatting and parsing;
- plural, gender, case, grammatical agreement, and other linguistic variation;
- bidirectional text and script support;
- localization QA, pseudo-localization, regression prevention, and release readiness.

The goal is not merely "translated strings". The goal is a product that feels as if it
was designed for the target locale.

# 1. Non-Negotiable Laws

These rules override convenience, framework defaults, and local implementation habits.

## 1.1 No user-visible hardcoded strings

NEVER hardcode user-visible English strings in production code.

ALWAYS use an i18n key for:

- visible copy;
- buttons;
- labels;
- headings;
- navigation;
- menus;
- dialogs;
- confirmations;
- warnings;
- errors displayed to users;
- validation messages;
- toasts;
- notifications;
- empty states;
- onboarding;
- tooltips;
- placeholders;
- accessible names;
- accessibility descriptions;
- screen-reader announcements;
- status text;
- table headers;
- filter names;
- sort labels;
- keyboard shortcut descriptions;
- settings descriptions;
- permission explanations;
- consent text;
- paywall/subscription text;
- transactional UI;
- emails generated by the product;
- push notifications;
- system-facing strings that can become user-visible later.

A string is user-visible if a user can reasonably encounter it through the product,
including assistive technology.

Non-user-visible strings may remain literals when appropriate, such as:

- internal identifiers;
- protocol constants;
- database field names;
- source-code comments;
- telemetry event names;
- machine-only error codes;
- test fixtures that intentionally test literal behavior;
- developer diagnostics that are guaranteed never to be surfaced.

If a diagnostic can reach the UI, it must be localized.

## 1.2 Preserve the English source exactly during migration

When migrating existing copy to i18n:

- preserve the English text byte-for-byte;
- do not "clean up" punctuation;
- do not change capitalization;
- do not rewrite wording;
- do not alter whitespace;
- do not improve grammar;
- do not change terminology;
- do not change spelling;
- do not change an existing English key.

Translation work and source-copy editing are separate tasks.

English is the intentional source copy. Build the localization system around it.

If product copy itself must change, that is a separate copy/content change and must be
explicitly requested.

## 1.3 Never encode locale logic in feature code

Feature/component/product code MUST NOT:

- inspect the current locale;
- compare locale strings;
- branch on language;
- call `Intl.PluralRules` or an equivalent plural engine directly;
- construct plural-category keys;
- select `.one`, `.two`, `.few`, `.many`, `.other`, etc.;
- implement language-specific grammar;
- decide decimal separators;
- decide date formats;
- decide currency placement;
- decide measurement units;
- manually transform localized text.

All locale complexity belongs behind the shared i18n/localization API.

Preferred conceptual API:

```text
language.t(key, params)
language.plural(baseKey, count, params)
language.number(value, options)
language.date(value, options)
language.time(value, options)
language.datetime(value, options)
language.currency(value, currency, options)
language.unit(value, unit, options)
language.list(values, options)
language.relativeTime(value, unit, options)
language.select(key, selector, params)   // only if required by the message system
```

The exact names may vary by stack. The architectural boundary must not.

## 1.4 Use complete phrases

Prefer complete translated phrases.

Bad:

```text
t("items.prefix") + count + t("items.suffix")
```

Good:

```text
language.plural("items", count, { count })
```

Bad:

```text
"Delete " + itemName + "?"
```

Good:

```text
language.t("delete-item-confirmation", { itemName })
```

Do not split sentences into grammatical fragments just because English makes that
convenient.

Placeholders should normally be limited to irreducible dynamic values:

- names;
- counts;
- dates;
- times;
- formatted numbers;
- URLs;
- paths;
- product names;
- user-provided content;
- code identifiers;
- other genuinely dynamic values.

The translator owns sentence structure.

## 1.5 Deepen the shared API when needed

If a translation cannot be expressed by the current i18n API:

DO NOT leak locale-specific machinery into product code.

Instead:

1. identify the linguistic requirement;
2. improve the shared i18n/message layer;
3. expose one typed operation that owns locale selection, fallback, plural resolution,
   interpolation, formatting, and validation;
4. keep feature code locale-agnostic.

A good localization architecture makes the difficult linguistic decision once.

# 2. Definitions

## 2.1 Language

A human language, such as English, French, Arabic, Japanese, or Thai.

## 2.2 Locale

A locale represents language plus relevant regional/script conventions.

Examples:

- `en`
- `en-US`
- `en-GB`
- `fr-FR`
- `fr-CA`
- `pt-BR`
- `pt-PT`
- `zh-Hans`
- `zh-Hant-TW`
- `sr-Latn`
- `sr-Cyrl`

Do not assume that language alone determines formatting or terminology.

## 2.3 Region

A geographic/market context that may change:

- currency;
- units;
- date conventions;
- week conventions;
- legal requirements;
- address formats;
- phone formats;
- payment methods;
- tax display;
- product availability;
- terminology;
- content;
- imagery;
- holidays.

## 2.4 Script

The writing system used by a locale.

Examples:

- Latin;
- Cyrillic;
- Arabic;
- Hebrew;
- Han;
- Devanagari;
- Thai.

Language, locale, and script are separate dimensions.

## 2.5 i18n

Internationalization: engineering the product so localization can happen without
rewriting product logic.

## 2.6 l10n

Localization: adapting the product for a particular language/locale/region/culture.

## 2.7 Translation

Rendering meaning from the source language into the target language.

Translation is one part of localization, not the whole of localization.

# 3. Architecture Principles

## 3.1 One localization boundary

Application code should depend on a shared localization service/module.

Conceptually:

```text
Feature
  ↓
Typed i18n API
  ↓
Message resolver
  ↓
Locale data + message catalog
  ↓
CLDR/ICU-backed formatting rules
```

The feature must not know how any layer below it works.

## 3.2 Source locale is authoritative

Choose one source locale, normally `en` or `en-US`.

The source locale is:

- complete;
- reviewed;
- stable;
- designer/writer controlled;
- the semantic source of truth;
- never rewritten solely to make another locale easier to translate.

Target locales adapt to the source.

## 3.3 Translation keys are stable identifiers

A key identifies a message, not its current English wording.

Do not rename keys because a translation is awkward.

Do not encode translations into keys.

Bad:

```text
button_text_click_here
english_delete_account
french_delete_account
```

Better:

```text
account.delete.confirm
account.delete.action
```

A key should describe product meaning/context, not grammar.

## 3.4 Avoid semantic key overloading

Do not reuse one key merely because two English strings happen to be identical.

For example, "Open" can be:

- open a file;
- open a menu;
- open a conversation;
- become available;
- an adjective.

Use separate semantic keys when context or grammatical role differs.

This gives translators enough context to choose the correct target-language form.

## 3.5 Avoid context-free generic keys

Avoid keys like:

```text
yes
no
open
close
name
status
```

unless the same message is genuinely identical in meaning, context, and grammatical use
throughout the product.

Prefer:

```text
dialog.confirm.yes
dialog.cancel
file.open.action
workspace.open.action
profile.name.label
```

The exact naming convention may differ, but semantic context must be preserved.

# 4. Message Design

## 4.1 Every message needs context

A translator must be able to understand:

- where the message appears;
- what action it represents;
- who is speaking;
- what the user is expected to do;
- what each placeholder means;
- grammatical role;
- capitalization requirements;
- length constraints;
- platform restrictions;
- whether the text is an accessible label;
- whether it is a title, sentence, tooltip, error, notification, etc.

Store developer comments/metadata when the localization format supports them.

Example conceptual metadata:

```text
Key: workspace.delete.confirmation
Source: "Delete {workspaceName}?"
Context: Confirmation dialog asking whether the user wants to permanently delete a workspace.
Placeholders:
  workspaceName = user-created workspace name
Tone: concise, neutral
```

## 4.2 Placeholder discipline

Every placeholder must have a semantic purpose.

Bad:

```text
"User {0} has {1}."
```

Good:

```text
"user.files.count"
params:
  userName
  count
```

Prefer named placeholders over positional placeholders.

Placeholder names should describe meaning, not implementation:

```text
{count}
{userName}
{workspaceName}
{date}
{duration}
```

Avoid:

```text
{x}
{v1}
{arg0}
```

## 4.3 Placeholder invariants

Localization tooling should validate:

- required placeholders;
- placeholder names;
- placeholder types;
- escaped markup;
- allowed formatting syntax;
- select/plural variables;
- ICU/Fluent syntax;
- links and URL placeholders;
- developer-defined non-translatable tokens.

A translation must not silently remove, rename, or corrupt required dynamic values.

## 4.4 Do not concatenate sentences

Never assemble grammatical sentences in application code.

Bad:

```text
"You have " + count + " new " + noun
```

Bad:

```text
prefix + username + suffix
```

Good:

```text
language.plural("notifications.unread", count, { count })
```

Good:

```text
language.t("welcome.user", { userName })
```

## 4.5 Do not force gender-neutral English into broken target language

If a target language requires grammatical gender, do not contort the English source
just to make translation easier.

The localization layer should support the required grammatical distinction.

Where necessary, use message selectors, grammatical variants, or a richer message
format.

# 5. Plurals

## 5.1 Never assume English plural rules

English commonly has `one` and `other`, but other locales may require:

- `zero`;
- `one`;
- `two`;
- `few`;
- `many`;
- `other`;

and may treat fractions differently.

Unicode CLDR defines locale-specific plural behavior and minimal-pair methodology.

The application must delegate plural selection to the localization layer.

## 5.2 Use the plural API

Product code:

```text
language.plural("cart.items", count, { count })
```

The product code must not do:

```text
if count == 1 ...
```

for linguistic purposes.

It must not do:

```text
key + ".one"
key + ".other"
```

It must not invoke a plural-rule engine directly.

## 5.3 Plural messages are complete messages

Good:

```text
cart.items:
  one: "{count} item"
  other: "{count} items"
```

A locale may then use its own required forms.

Do not assume every locale has exactly the same variants.

## 5.4 Zero is not universally "other"

A product may need a dedicated zero message for natural UX:

```text
"You have no messages."
```

rather than:

```text
"You have 0 messages."
```

This is a content decision, not a universal grammatical rule.

## 5.5 Fractions matter

Localization systems must consider:

- `1`;
- `1.0`;
- `1.5`;
- `2`;
- `2.0`;
- locale-specific decimal behavior.

Do not manually classify fractions.

## 5.6 Ordinals are different

Cardinal:

```text
1 item
2 items
```

Ordinal:

```text
1st
2nd
3rd
```

Do not reuse cardinal plural logic for ordinal messages.

# 6. Formatting and Regionalization

NEVER hand-format locale-sensitive data in product code.

Use locale-aware shared APIs.

## 6.1 Numbers

Localize:

- decimal separator;
- grouping separator;
- grouping strategy;
- significant digits;
- decimal digits;
- compact notation;
- percentage;
- scientific notation where relevant;
- negative numbers;
- accounting formats.

Never assume:

```text
1,234.56
```

is universally correct.

## 6.2 Currency

Currency has multiple dimensions:

- currency code;
- symbol;
- symbol placement;
- spacing;
- decimal precision;
- rounding;
- accounting format;
- locale;
- business rules.

Never treat `$` as synonymous with USD.

Use ISO currency codes internally and locale-aware presentation externally.

Do not infer currency from a symbol.

## 6.3 Dates

Do not hardcode:

```text
MM/DD/YYYY
DD/MM/YYYY
YYYY-MM-DD
```

for presentation.

Use locale-aware date formatting.

Keep machine dates/timestamps separate from presentation.

## 6.4 Times

Handle:

- 12/24-hour conventions;
- locale-specific day periods;
- seconds visibility;
- time zones;
- daylight-saving transitions;
- ambiguous/nonexistent local times.

Never assume the user's locale is the server locale.

## 6.5 Time zones

Store instants in a stable representation.

Convert to the user's intended time zone for presentation.

Distinguish:

- instant;
- UTC offset;
- time zone;
- calendar date;
- local wall-clock time.

A date such as "2026-08-23" may represent a calendar day rather than an instant.

## 6.6 Relative time

Use localization APIs for:

- yesterday;
- tomorrow;
- 3 hours ago;
- in 5 minutes;
- last week.

Do not construct these phrases manually.

## 6.7 Units

Localize:

- length;
- mass;
- temperature;
- speed;
- area;
- volume;
- digital storage;
- duration;
- energy;
- pressure;
- other domain units.

Separate:

1. the canonical value;
2. the chosen unit;
3. the localized display.

Do not hardcode "km", "mi", "kg", "lb", etc. into arbitrary UI strings when the
unit is locale-dependent.

## 6.8 Measurement systems

Region may determine metric/US customary/other conventions.

Do not assume:

```text
language == measurement system
```

Regional preference and user preference may both matter.

## 6.9 Lists

Use locale-aware list formatting for:

- conjunctions;
- disjunctions;
- punctuation;
- pair formatting;
- short/narrow list styles.

Do not manually join arrays with `", "` or `" and "`.

## 6.10 Collation and sorting

Do not sort user-visible localized text with byte/Unicode code-point ordering.

Use locale-aware collation when the product intends linguistic ordering.

Be explicit about whether sorting is:

- machine identifier order;
- locale-aware display order;
- numeric order;
- chronological order;
- domain-specific order.

## 6.11 Case conversion

Never use ASCII assumptions for upper/lower/title casing.

Case behavior can vary by locale and script.

Do not implement localized casing with simplistic string operations.

# 7. Locale and Locale Negotiation

## 7.1 Locale resolution order

Define one deterministic policy, for example:

```text
explicit user preference
→ account preference
→ application preference
→ operating-system/browser preference
→ supported locale fallback
→ source locale
```

The exact order is a product decision.

It must be documented and tested.

## 7.2 Never blindly trust requested locales

Normalize and validate locale identifiers.

Resolve unsupported locales to supported locales using an explicit policy.

Example:

```text
fr-CA → fr-CA if supported
fr-CA → fr if only French is supported
fr-CA → en if neither is supported
```

Do not assume every language-region combination exists.

## 7.3 Language fallback is not universal

Fallback may involve:

- language;
- script;
- region;
- parent locale;
- source locale.

Do not implement ad-hoc fallback chains in feature code.

## 7.4 Locale identifiers

Use standards-compliant locale identifiers.

Do not invent internal variants such as:

```text
english_us
french_canada
```

unless they are separate internal product identifiers explicitly mapped to standards-based
locales.

# 8. Scripts and Bidirectional Text

Localization is incomplete until non-Latin scripts are tested.

Support:

- right-to-left languages;
- mixed-direction text;
- Arabic;
- Hebrew;
- CJK;
- Indic scripts;
- Thai and scripts without whitespace word boundaries;
- combining marks;
- diacritics;
- emoji;
- full-width characters;
- complex shaping.

## 8.1 RTL

Do not assume that "RTL" means simply reversing the entire interface.

Use semantic layout directions:

```text
start / end
```

instead of blindly using:

```text
left / right
```

where the layout should mirror.

Do not mirror:

- logos unless explicitly designed to;
- media controls where semantics require stable orientation;
- numbers;
- text glyphs;
- universally directional symbols;
- brand assets.

Test bidi isolation around dynamic user content.

## 8.2 Mixed-direction content

User-provided values may contain different scripts.

Protect surrounding text from bidi corruption.

Use appropriate bidi isolation mechanisms provided by the platform/message formatter.

## 8.3 Typography

Check:

- fonts;
- glyph coverage;
- fallback fonts;
- line height;
- shaping;
- punctuation;
- font weight;
- text rendering;
- baseline alignment.

Never assume a Latin font covers the target locale.

---

# 9. UI Layout and String Expansion

Translations may be:

- much longer than English;
- much shorter;
- multi-line;
- visually asymmetric;
- taller due to script/font metrics.

Never design UI around the exact width of English text.

Test:

- buttons;
- tabs;
- navigation;
- cards;
- dialogs;
- tables;
- mobile layouts;
- desktop layouts;
- narrow windows;
- large accessibility fonts;
- zoom;
- responsive layouts.

Avoid hardcoded widths for text-heavy controls.

Prefer:

- flexible layout;
- wrapping where appropriate;
- truncation only when semantically safe;
- tooltips/accessibility labels for truncated content;
- minimum/maximum constraints;
- content-driven sizing.

---

# 10. Accessibility Is Localized Content

Accessibility strings are first-class localized strings.

Localize:

- accessible names;
- descriptions;
- roles where applicable;
- state announcements;
- screen-reader status messages;
- keyboard shortcut descriptions;
- alternative text;
- captions;
- error descriptions.

Do not leave accessibility text in English while visible UI is translated.

Accessibility content must use the same terminology and localization standards as the
visual UI.

# 11. Terminology and Glossaries

## 11.1 Terminology is a product asset

Maintain a terminology system containing:

- source term;
- approved target term(s);
- forbidden terms;
- grammatical information where useful;
- product context;
- notes;
- locale/region;
- source/reference;
- status;
- reviewer.

## 11.2 Do not translate word-by-word

A glossary hit is evidence, not permission to translate mechanically.

Translate the complete phrase in context.

Terse labels require special care.

Examples of terms that require contextual review:

- session;
- prompt;
- agent;
- model;
- fork;
- shell;
- terminal;
- workspace;
- worktree;
- deployment;
- build;
- branch;
- commit;
- package;
- plugin.

The same English word may require different target-language terms depending on:

- grammatical role;
- product meaning;
- platform convention;
- developer audience;
- region.

## 11.3 Developer-facing terminology

For technical/developer products:

1. prefer established terminology used by the target language's developer community;
2. cross-check maintained localized developer products;
3. prefer existing terminology over literal dictionary translations;
4. retain English loanwords/acronyms when they are established practice;
5. never invent a translation merely because a dictionary offers one.

Recommended corpus strategy:

- Firefox localization;
- KDE localization;
- VS Code localization;
- at least two independent maintained corpora where available.

## 11.4 Product names

Do not translate product names unless the brand/product policy explicitly says so.

Preserve:

- product names;
- company names;
- provider names;
- trademarks;
- URLs;
- domain names;
- code identifiers.

Check the relevant brand guide.

# 12. Translation Evidence and Research

## 12.1 Never translate from model knowledge alone

AI-generated translation is a draft, not authoritative linguistic evidence.

For each locale, verify terminology and grammar against authoritative or maintained
sources.

Preferred evidence hierarchy:

1. official language authority / national standard;
2. official product/platform localization guidance;
3. maintained professional localization corpus;
4. established developer products;
5. reputable dictionaries/terminology databases;
6. native-speaker review;
7. general web usage as supporting evidence only.

## 12.2 Required cross-checks

Use relevant sources from the following families.

### Unicode CLDR

Use CLDR for:

- plural rules;
- number formatting;
- date/time patterns;
- currencies;
- units;
- locale data;
- language/region conventions;
- locale-specific behavior.

CLDR is the machine-readable standards/data authority for locale behavior.

### Microsoft Localization Style Guides

Use the Microsoft style guides for:

- language-specific style;
- technical terminology;
- tone;
- capitalization;
- punctuation;
- formatting;
- locale conventions.

### Apple localization guidance

Use Apple guidance for:

- application localization;
- platform UI terminology;
- Apple-specific conventions;
- string localization;
- locale-aware app behavior.

### Mozilla

Use:

- Mozilla localization style guides;
- Mozilla Pontoon;
- Firefox localized strings;
- Firefox localization source;
- Firefox localization documentation.

Firefox is especially valuable as a large, maintained multilingual technical-product corpus.

### Developer corpora

Cross-check maintained localized products such as:

- Firefox;
- KDE;
- VS Code.

Use at least two independent corpora when available.

## 12.3 Language authorities

Also consult the relevant official authority/dictionary for the target locale, where available.

Examples include:

- Spanish: RAE / Fundéu;
- French: FranceTerme and relevant French terminology authorities;
- German: Duden;
- Turkish: Türk Dil Kurumu (TDK);
- Finnish: Kotus / Kielitoimiston sanakirja;
- Norwegian: Språkrådet / Bokmålsordboka;
- Polish: Rada Języka Polskiego / PWN;
- Russian: relevant Russian language authorities and maintained dictionaries;
- Arabic: relevant national/Arabic language academies;
- Ukrainian: Ukrainian Orthography and authoritative dictionaries;
- Traditional Chinese (Taiwan): Taiwan Ministry of Education dictionaries;
- Thai: Royal Society of Thailand.

The exact authority depends on locale.

## 12.4 Source-of-truth rule

The English dictionary/source text defines the semantic intent.

Target-language authorities define how that meaning should naturally be expressed.

Do not alter source semantics to match a target-language dictionary.

Preserve:

- placeholders;
- code identifiers;
- product names;
- keyboard labels;
- URLs;
- protocol tokens.

# 13. Translation Workflow

Use this lifecycle.

## Phase 1 — Inventory

Find all user-visible content:

- source code;
- templates;
- frontend components;
- backend-generated UI messages;
- validation errors;
- emails;
- notifications;
- push messages;
- accessibility content;
- metadata displayed in UI;
- generated documents;
- help content;
- marketing content where in scope.

Search for:

- string literals;
- template text;
- error messages;
- fallback literals;
- concatenated messages;
- locale branches;
- manual date/number formatting.

## Phase 2 — Classify

For every string classify:

- UI copy;
- error;
- accessibility;
- notification;
- transactional;
- marketing;
- legal;
- developer-facing;
- machine-only;
- product name;
- provider/tool name;
- URL;
- code token.

Only user-facing content belongs in normal translation catalogs.

## Phase 3 — Extract

Create stable semantic keys.

Add context and placeholder metadata.

Do not change English source copy.

## Phase 4 — Implement

Replace source literals with shared i18n calls.

Do not introduce locale branches.

Move formatting into shared locale-aware APIs.

## Phase 5 — Translate

Translate complete messages.

Respect:

- context;
- tone;
- terminology;
- grammar;
- placeholders;
- product terminology;
- platform terminology;
- locale conventions.

## Phase 6 — Verify

Check:

- placeholder parity;
- missing keys;
- duplicate/ambiguous keys;
- malformed messages;
- plural coverage;
- formatting;
- bidi;
- UI expansion;
- accessibility;
- terminology consistency.

## Phase 7 — Native review

Native or expert locale reviewers should focus on:

- naturalness;
- grammar;
- register;
- terminology;
- cultural appropriateness;
- regional correctness;
- ambiguous strings;
- suspicious retained English.

## Phase 8 — Release audit

Before declaring a locale ready:

- audit recurring concepts;
- audit every value still equal to English;
- classify every retained English value;
- resolve unexplained leftovers;
- run pseudo-localization;
- test locale formatting;
- test RTL where relevant;
- test accessibility;
- test all major flows.

# 14. English-Equals-English Audit

A translated catalog often contains accidental untranslated strings.

Before locale readiness, find every target value equal to the source English value.

Do NOT automatically translate all matches.

Classify each retained English value as:

1. product name;
2. company/provider/tool name;
3. URL/domain;
4. code token;
5. keyboard legend;
6. acronym;
7. asset name;
8. established English borrowing;
9. intentionally preserved technical term;
10. intentionally preserved proper noun;
11. genuinely untranslated content.

Everything outside the justified categories must be reviewed.

Record the reason for intentionally retained English.

---

# 15. Translation Memory and Consistency

Maintain consistency for recurring concepts.

If "workspace" is translated one way in:

- navigation;
- settings;
- errors;
- onboarding;
- documentation;

do not casually introduce a second translation.

Exceptions are allowed when grammar/context requires them.

The glossary must distinguish:

- preferred term;
- inflected form;
- context-specific variant;
- prohibited synonym.

Consistency is a quality property, but natural grammar takes priority over blind
one-to-one term replacement.

---

# 16. Machine Translation and AI

AI/MT may accelerate localization but must not become the final authority.

AI may:

- propose translations;
- detect untranslated strings;
- find inconsistent terminology;
- identify placeholder issues;
- propose glossary entries;
- explain grammar;
- compare corpora;
- generate review reports;
- perform mechanical migration.

AI must not:

- invent locale-specific grammar rules;
- fabricate authoritative terminology;
- declare a locale correct without evidence;
- rewrite source English without permission;
- silently change product terminology;
- choose a plural category manually;
- replace native review for high-impact content.

Every AI translation should be treated as a candidate until validated.

# 18. Locale-Specific Style

Every supported locale should have a locale profile.

At minimum define:

- language;
- region;
- script;
- formality;
- tone;
- capitalization;
- punctuation;
- quotation marks;
- date conventions;
- time conventions;
- number conventions;
- currency;
- measurement system;
- address conventions;
- name conventions;
- developer terminology;
- product terminology;
- accessibility conventions;
- forbidden terms;
- preferred terms;
- legal/content constraints;
- special cultural considerations.

Do not assume a language has one universal style across all regions.

---

# 19. Content That Is Not "Just Translation"

Localization review must consider:

## 19.1 Icons and imagery

Check whether:

- symbols have different meanings;
- hand gestures are culturally appropriate;
- colors carry different connotations;
- illustrations imply inappropriate cultural assumptions;
- screenshots contain localized text;
- text embedded in images requires localization.

## 19.2 Names and addresses

Names and addresses are culturally structured.

Do not assume:

```text
first name + last name
street + number + city
```

is universal.

## 19.3 Phone numbers

Do not assume fixed:

- digit count;
- prefix length;
- separators;
- formatting.

Store phone numbers canonically where appropriate and format them by region.

## 19.4 Postal codes

Do not assume:

- numeric-only;
- fixed length;
- one format.

## 19.5 Calendars

Some products require calendars beyond Gregorian.

Use locale/user settings and domain requirements rather than hardcoding assumptions.

## 19.6 Week rules

Week start and week numbering can differ by locale.

Do not hardcode Monday/Sunday unless it is a product requirement independent of locale.

## 19.7 Holidays

Do not assume holidays are universal.

Holiday behavior may depend on:

- region;
- locale;
- calendar;
- business rules.

---

# 20. Legal, Compliance, and Market Adaptation

Localization can affect legal/compliance content.

Treat these as product/legal requirements, not translator preferences:

- consent;
- privacy notices;
- cookies;
- terms;
- tax;
- invoices;
- consumer rights;
- accessibility requirements;
- age restrictions;
- financial disclosures;
- subscription cancellation;
- required warnings.

Never ask a translator to make a legal policy decision.

The legal owner must approve legal localization.

---

# 21. Error Messages

Errors are user-visible product copy.

Never expose raw internal errors directly to users.

Bad:

```text
database: unique constraint violation on users_email_key
```

Better:

```text
language.t("account.email.already-used")
```

Keep machine diagnostics separately:

```text
errorCode = USER_EMAIL_ALREADY_USED
debugDetails = ...
userMessageKey = account.email.already-used
```

This gives localization a stable boundary.

Errors should tell the user:

- what happened;
- what they can do next;
- what information is useful.

---

# 22. Backend and API Design

Localization must remain possible even when messages originate outside the UI layer.

Prefer APIs returning structured errors:

```text
{
  code: "workspace.not_found",
  params: {
    workspaceName: "..."
  }
}
```

rather than:

```text
{
  message: "Workspace not found."
}
```

The presentation layer localizes the code.

For server-rendered applications, the same principle applies:

```text
server/domain error
→ stable error code + structured parameters
→ localization layer
→ user-visible message
```

Do not force every backend service to know every human language.

---

# 23. Logging and Telemetry

Logs are normally not localized.

Telemetry identifiers must not be translated.

Keep:

- stable event names;
- stable error codes;
- stable metrics;
- stable protocol identifiers.

Localize only the user-facing representation.

This separation prevents analytics and debugging from becoming language-dependent.

---

# 24. Security and Localization

Localization can introduce security bugs.

Validate:

- Unicode normalization;
- confusable characters where relevant;
- bidi control characters;
- unsafe interpolation;
- HTML/Markdown escaping;
- URL encoding;
- filename rendering;
- shell/command rendering;
- user-generated content;
- translated HTML attributes.

Never trust a translation as safe merely because it is "static".

Translations can contain:

- apostrophes;
- quotes;
- braces;
- markup;
- directionality;
- special Unicode characters.

Use typed/escaped rendering appropriate to the target context.

---

# 25. Formatting vs Translation

Keep these responsibilities separate.

Translation:

```text
"Your balance is {amount}."
```

Formatting:

```text
amount → locale-aware currency
```

The final message should combine them through the localization layer.

Do not pre-format values in a locale-insensitive way and then inject them.

Bad:

```text
amount = "$1,234.50"
language.t("balance", { amount })
```

Better:

```text
language.t("balance", {
  amount: language.currency(1234.5, "USD")
})
```

Or use a message system capable of typed formatting.

---

# 26. Testing Strategy

Localization requires automated and human QA.

## 26.1 Static checks

CI should detect:

- hardcoded user-visible strings;
- missing translation keys;
- unused keys where policy requires cleanup;
- duplicate keys;
- malformed messages;
- invalid locale identifiers;
- placeholder mismatch;
- invalid plural/select syntax;
- invalid markup;
- untranslated strings;
- accidental source changes;
- locale file corruption.

## 26.2 Runtime checks

Test:

- fallback;
- missing translations;
- malformed translations;
- unsupported locales;
- locale switching;
- plural resolution;
- number formatting;
- date/time formatting;
- currency;
- units;
- relative time;
- lists;
- bidi;
- accessibility labels.

## 26.3 Pseudo-localization

Use pseudo-locales to reveal layout assumptions.

Pseudo-localization should simulate:

- text expansion;
- accented characters;
- non-ASCII characters;
- mixed scripts;
- RTL;
- long words;
- special punctuation.

Typical pseudo-localization goals:

- detect clipped strings;
- detect hardcoded English;
- detect encoding bugs;
- detect concatenation;
- detect fixed-width UI;
- detect broken placeholders.

## 26.4 Boundary values

Test plural/formatting values such as:

```text
0
1
2
3
4
5
10
11
12
20
21
22
100
101
1.0
1.1
1.5
2.0
```

The exact test set should be generated from CLDR rules for supported locales.

Do not assume these examples cover every locale.

## 26.5 Visual QA

Review screenshots/runs for:

- clipping;
- wrapping;
- overlap;
- truncation;
- alignment;
- RTL mirroring;
- incorrect punctuation;
- font fallback;
- line height;
- modal overflow;
- mobile layout;
- accessibility zoom.

# 27. CI Quality Gates

A locale should not ship if required gates fail.

Recommended gates:

### Gate A — Source integrity

- English source unchanged unless explicitly modified.
- Keys stable.

### Gate B — Extraction

- no unexplained hardcoded user-visible strings.

### Gate C — Catalog integrity

- all required keys present;
- no malformed messages;
- no placeholder mismatch.

### Gate D — Linguistic integrity

- plural/select variants valid;
- terminology checks pass;
- suspicious English leftovers reviewed.

### Gate E — Formatting

- dates/numbers/currency/units tested.

### Gate F — UI

- pseudo-localization passes;
- representative target-locale screenshots pass;
- RTL passes for RTL locales.

### Gate G — Accessibility

- localized accessible names/descriptions present;
- screen-reader flows tested.

### Gate H — Human review

- required native/expert review completed.

# 28. Migration Playbook

When adding i18n to an existing application:

## Step 1 — Inventory

Find all visible literals and formatting logic.

## Step 2 — Freeze source copy

Treat current English as authoritative.

Do not improve it during migration.

## Step 3 — Extract

Create semantic keys while preserving exact English values.

## Step 4 — Replace

Replace UI literals with the shared i18n API.

## Step 5 — Refactor concatenation

Convert fragments into complete messages.

## Step 6 — Centralize formatting

Move dates, numbers, currencies, units, lists, and relative times into locale-aware
formatting APIs.

## Step 7 — Remove locale branches

Move language/region decisions into the shared localization layer.

## Step 8 — Add tests

Add static checks, placeholder checks, plural tests, and pseudo-localization.

## Step 9 — Translate

Only after the source catalog is structurally sound.

## Step 10 — Audit

Run the English-equals-English audit and terminology consistency audit.

# 29. Anti-Patterns

## Anti-pattern: hardcoded UI text

```text
button.text = "Save"
```

Use an i18n key.

## Anti-pattern: concatenation

```text
"Hello " + name + "!"
```

Use a complete message.

## Anti-pattern: locale branch

```text
if locale == "fr" ...
```

Move this into localization data/API.

## Anti-pattern: manual plural

```text
count == 1 ? "item" : "items"
```

Use plural resolution.

## Anti-pattern: plural suffix keys

```text
items.one
items.other
```

Feature code must not construct/select these keys.

The underlying message format may contain plural variants, but the caller must invoke
the typed plural API.

## Anti-pattern: manual date formatting

```text
day + "/" + month + "/" + year
```

Use locale-aware date formatting.

## Anti-pattern: symbol-based currency

```text
"$" + amount
```

Use currency-aware formatting.

## Anti-pattern: manual list joining

```text
items.join(", ")
```

Use locale-aware list formatting.

## Anti-pattern: source rewriting for translation

Changing:

```text
"Delete workspace?"
```

to:

```text
"Are you sure you want to delete this workspace?"
```

during localization is forbidden unless explicitly requested as a copy change.

## Anti-pattern: translating terminology literally

Do not translate technical terminology word-for-word without checking established
target-language usage.

## Anti-pattern: assuming locale from language

Do not infer currency, date format, or measurement system solely from language.

# 30. Definition of Done

A localization implementation is complete only when:

- [ ] All user-visible copy uses i18n keys.
- [ ] English source values are preserved byte-for-byte during migration.
- [ ] Existing English keys remain stable.
- [ ] Feature code does not inspect locale.
- [ ] Feature code does not implement plural rules.
- [ ] Feature code does not construct plural-category keys.
- [ ] Complete phrases are used instead of grammatical fragments.
- [ ] Dynamic values are explicit placeholders.
- [ ] Placeholder contracts are validated.
- [ ] Locale-aware number formatting exists.
- [ ] Locale-aware date/time formatting exists.
- [ ] Locale-aware currency formatting exists.
- [ ] Locale-aware unit formatting exists where needed.
- [ ] Locale-aware list formatting exists where needed.
- [ ] Locale negotiation and fallback are deterministic.
- [ ] RTL/script support is tested where applicable.
- [ ] Accessibility strings are localized.
- [ ] Pseudo-localization has been run.
- [ ] Hardcoded-string checks exist in CI.
- [ ] Translation catalogs pass structural validation.
- [ ] English-equals-English audit is complete.
- [ ] Retained English is classified and justified.
- [ ] Recurring terminology is consistent.
- [ ] Locale-specific terminology was checked against authoritative sources.
- [ ] Technical terminology was cross-checked against maintained developer corpora.
- [ ] Uncertain/region-specific terms are documented.
- [ ] Native/expert review is complete for the required scope.
- [ ] Visual QA is complete.
- [ ] Legal/compliance localization is separately approved where applicable.

# 31. Recommended Abstract API Contract

A programming-language-agnostic localization library should conceptually provide:

```text
Language
├── locale() -> Locale
├── supportedLocales() -> []Locale
├── t(Key, Params) -> LocalizedText
├── plural(Key, Count, Params) -> LocalizedText
├── select(Key, Selector, Params) -> LocalizedText
├── number(Value, NumberOptions) -> LocalizedText
├── integer(Value, NumberOptions) -> LocalizedText
├── percent(Value, PercentOptions) -> LocalizedText
├── currency(Value, CurrencyCode, CurrencyOptions) -> LocalizedText
├── unit(Value, Unit, UnitOptions) -> LocalizedText
├── date(Value, DateOptions) -> LocalizedText
├── time(Value, TimeOptions) -> LocalizedText
├── datetime(Value, DateTimeOptions) -> LocalizedText
├── relativeTime(Value, Unit, RelativeTimeOptions) -> LocalizedText
├── list(Values, ListOptions) -> LocalizedText
├── localeName(Locale) -> LocalizedText
└── direction() -> LTR | RTL
```

This is an architectural contract, not a requirement to expose exactly these methods.

The implementation may use ICU, CLDR, Fluent, ICU MessageFormat, MessageFormat 2,
platform APIs, or another standards-compliant system.

The application layer must not depend on which implementation is underneath.

---

# 32. Typed Message Contract

Where the programming language supports typing, prefer compile-time or build-time
validation.

Conceptually:

```text
Key<"workspace.delete.confirmation">:
  workspaceName: String

Key<"workspace.members.count">:
  count: Number
```

Invalid:

```text
t("workspace.delete.confirmation", {})
```

Invalid:

```text
t("workspace.delete.confirmation", {
  name: workspaceName
})
```

Valid:

```text
t("workspace.delete.confirmation", {
  workspaceName
})
```

The goal is to make localization errors detectable before production.

---

# 33. Message Format Requirements

A message format should support, directly or through the shared API:

- named variables;
- plural selection;
- select/variant logic;
- nested messages;
- number formatting;
- date/time formatting;
- currency formatting;
- escaping;
- markup-safe interpolation;
- locale-aware behavior;
- developer comments/context;
- placeholder validation.

Prefer standards-based or mature message systems over home-grown grammar engines.

Do not invent a custom plural algorithm.

---

# 34. Source and Translation File Rules

Regardless of file format:

- source locale is authoritative;
- keys are stable;
- translations are separate from product logic;
- translators receive context;
- placeholders are explicit;
- comments are preserved;
- product names are marked where necessary;
- non-translatable tokens are marked;
- malformed messages fail CI;
- locale files can be reviewed independently.

Keep translation changes reviewable independently from application logic whenever
possible.

---

# 35. Release Strategy

Localization can be shipped progressively.

Recommended model:

```text
source change
→ extraction
→ translator notification
→ translation
→ automated validation
→ linguistic review
→ integration
→ visual QA
→ release
```

For incomplete locales, define explicit product behavior.

Possible states:

- fully supported;
- supported with fallback;
- beta;
- machine-translated draft;
- unavailable.

Never let an incomplete catalog silently appear complete.

---

# 36. Fallback Philosophy

Fallback should preserve functionality, but not hide localization defects.

Recommended:

- production can fall back safely;
- CI still reports missing translations;
- missing target strings are visible to localization tooling;
- fallback is observable through telemetry or diagnostics where appropriate;
- users should not be exposed to raw translation keys.

Never display:

```text
workspace.delete.confirmation
```

as the user-facing fallback.

---

# 37. Translation Key Naming Convention

Choose one convention and enforce it consistently.

Recommended semantic hierarchy:

```text
<domain>.<feature>.<purpose>
```

Examples:

```text
account.email.invalid
account.email.already-used

workspace.create.title
workspace.create.action
workspace.delete.confirmation
workspace.delete.success

settings.language.label
settings.language.description
```

For messages whose meaning depends on context, add enough semantic specificity.

Avoid encoding locale, language, grammatical gender, or plural category in the caller's
key.

Bad:

```text
workspace.delete.confirmation.fr
items.one
items.other
```

Good:

```text
workspace.delete.confirmation
workspace.members.count
```

# 38. Review Heuristics

When reviewing a localization PR, ask:

### Engineering

1. Is any user-visible string still hardcoded?
2. Is any locale branch present?
3. Is any formatting manually constructed?
4. Are placeholders typed/validated?
5. Are plural rules delegated?
6. Is fallback deterministic?
7. Are keys stable?

### Linguistic

1. Does the translation convey the complete source meaning?
2. Is it natural for the locale?
3. Is the register correct?
4. Is terminology consistent?
5. Are technical terms established in the target community?
6. Were authoritative references consulted?
7. Are region-specific differences respected?

### UX

1. Does the translation fit?
2. Does it wrap safely?
3. Does it work in narrow layouts?
4. Does it work with large text?
5. Does RTL work?
6. Are accessibility labels natural?
7. Are icons/images culturally appropriate?

### QA

1. Were placeholder checks run?
2. Were plural boundary values tested?
3. Was pseudo-localization run?
4. Was the English-equals-English audit run?
5. Was native/expert review completed?

# 39. Localization Decision Tree

When encountering text:

```text
Is it user-visible?
 ├─ No → keep machine/developer literal if appropriate.
 └─ Yes
     ↓
 Does it already have an i18n key?
 ├─ Yes → use the key.
 └─ No
     ↓
 Create semantic key + preserve exact English source.
     ↓
 Is the message grammatical/complete?
 ├─ No → refactor into a complete message.
 └─ Yes
     ↓
 Does it depend on count?
 ├─ Yes → shared plural API.
 └─ No
     ↓
 Does it require selection/gender/case/etc.?
 ├─ Yes → deepen shared message API.
 └─ No
     ↓
 Does it contain locale-sensitive formatting?
 ├─ Yes → shared locale formatter.
 └─ No
     ↓
 Translate using context + authoritative evidence.
     ↓
 Validate + review + visual QA.
```

# 40. Golden Rule for AI Agents

When an AI agent is asked to modify or build localized software:

> Make the product locale-agnostic in code and locale-aware at the localization
> boundary.

The agent must resist the temptation to solve localization problems with:

- string concatenation;
- locale branches;
- hardcoded translations;
- English-only assumptions;
- manual plural rules;
- manual formatting;
- literal technical terminology;
- source-copy rewrites;
- unverified dictionary translations.

The correct response to a missing localization capability is to improve the shared
localization abstraction, not to bypass it.

---

# 41. Compact Agent Checklist

Before changing localized application code:

- [ ] Is the content user-visible?
- [ ] If yes, does it have an i18n key?
- [ ] Is the English source unchanged?
- [ ] Is the key semantic and stable?
- [ ] Is the message complete?
- [ ] Are placeholders irreducibly dynamic?
- [ ] Is pluralization delegated?
- [ ] Is locale selection delegated?
- [ ] Is formatting delegated?
- [ ] Is the target terminology evidenced?
- [ ] Were CLDR rules consulted where relevant?
- [ ] Were authoritative language sources consulted?
- [ ] Were Microsoft/Apple/Mozilla resources checked where relevant?
- [ ] Were maintained developer corpora checked?
- [ ] Are retained English values justified?
- [ ] Were RTL/expansion/accessibility concerns considered?
- [ ] Will CI catch this class of localization regression?

If any answer is "no", the localization work is not finished.

Use current official resources when validating implementation or terminology:

- Unicode CLDR — locale data, plural rules, number/date/unit conventions.
- Microsoft Localization Style Guides — language-specific localization conventions.
- Apple Developer Localization — Apple platform localization and internationalization guidance.
- Mozilla Localization / Firefox Source Docs — localization architecture and workflow.

# 43. Final Principle

Localization is successful when the user does not feel translated.

The best localized product:

- speaks naturally;
- formats information correctly;
- respects regional conventions;
- uses familiar terminology;
- behaves correctly for the user's script and direction;
- remains accessible;
- survives text expansion;
- handles plural and grammatical variation;
- preserves product meaning;
- does not expose implementation details;
- and feels native to the locale.

Build the system so that product engineers write intent, localization specialists
write language, and the localization runtime owns the linguistic complexity.
